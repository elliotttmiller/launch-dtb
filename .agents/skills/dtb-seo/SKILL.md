# DTB SEO

## Evidence boundary
Use the actual route/rendering pipeline, metadata/structured-data implementation, sitemap/robots behavior and canonical catalog relationships. Separate what source proves from what requires deployed runtime, crawler or search-console evidence. Never fabricate index status, ranking, price, availability, ratings, product identifiers, schema validity or route behavior.

## Technical audit
Evaluate crawl/index eligibility, canonical URLs, robots directives, sitemap inclusion, redirects/status codes, duplicate/thin route variants, metadata uniqueness, structured data consistency with visible authoritative content, internal linking/discoverability, media/performance impact, and Core Web Vitals when measurable.

Session/account/cart/checkout/order/status/preview/operator routes are not public indexable inventory unless active source explicitly changes that contract. Structured product data must reflect visible Woo/catalog facts and must not invent reviews, offers or availability.

Internal product/part/compatibility relationships should use canonical catalog/schematic mechanisms rather than hard-coded UI link graphs. Avoid mass-generated landing pages without distinct user value and authoritative data.

## Output
Cite exact source paths/symbols for source-verifiable findings. Label runtime/search-engine verification separately and specify how to verify it. Prioritize by indexability/correctness, material discoverability, structured-data integrity and measured performance—not SEO folklore. Use scoped task context only when the audit genuinely needs persistence.
