# Checkout Refactor/Redesign — Handoff Document

Status: **Audit + investigation complete. No code changes made yet.** This document is the continuation point for a new chat session.

## Goal

DTB wants a full top-to-bottom refactor, redesign, and rebuild of the checkout form's UI/UX — architecture, styling, layout, and interaction — with modern, polished, professional mobile-first styling and animation. The original trigger question was: should the current mobile "step wizard" become a single-page fluid/responsive checkout with smooth accordion expand/collapse per section instead?

This session did **not** write or edit any implementation files. It produced two full audits (one prior, one WooCommerce-core-grounded) and a technical verdict. The next session's job is to turn the verdict below into an actual implementation plan and execute it.

## What currently exists (confirmed via direct source reads, not assumption)

Checkout is **not a real multi-step wizard** — it's a single WooCommerce Checkout Block DOM (all fields mounted, Stripe Payment Element never unmounted) with a **mobile-only JS overlay** (`assets/checkout/checkout.js`, ~551 lines, in the `drywall-toolbox` theme, `< 768px` only) that:
- Classifies WooCommerce Blocks' own real per-block identity classes (`wp-block-woocommerce-checkout-*-block`) into Contact/Shipping/Payment groups (`classifyStepGroups()`), added as of a same-day **Redesign v17** fix.
- Hides non-active groups via `inert` + `[data-dtb-step-hidden]` (not DOM removal — Stripe's element stays mounted).
- Builds its own progress rail (`buildRail()`) and sticky Back/Continue action bar (`buildActionBar()`), gates "Continue" with scoped `checkValidity()` (`canAdvanceFrom()`).
- Fails safe to plain single-scroll checkout on tablet/desktop (≥768px) and whenever classification can't find real Contact/Payment content (`reconcile()`).

Supporting files, all in `drywalltoolbox/wp/wp-content/themes/drywall-toolbox/`:
- `templates/checkout/native-checkout.php` — thin shell, branded top bar only, no field/step logic. Server-rendered, **outside the React SPA's webpack build entirely** (no Vite/Tailwind/PostCSS access, can't reference `frontend/src/styles/*` tokens or the self-hosted font build — loads Google Fonts instead).
- `assets/checkout/checkout.css` (~1119 lines) — mobile-first, restyles Woo's own published class names by name only. Has its own **separate token set** (`--dtb-ink`, `--dtb-accent`, `--dtb-radius-lg` etc.) that looks similar to but is **not the same as** `frontend/src/styles/storefront-tokens.css`'s tokens (same prefix, different values — e.g. `--dtb-radius-lg` is 18px here vs 16px in the SPA tokens). No motion-duration/easing tokens — hardcodes `160ms ease` everywhere; the SPA's canonical motion system (`--dtb-ease`, `--dtb-ease-standard`, `--dtb-ease-emphasized`, `--dtb-ease-soft`, `--dtb-ease-exit`, `--dtb-fast`(160ms)/`--dtb-normal`(280ms)/`--dtb-slow`(420ms) in `storefront-tokens.css`) is never referenced. One harmless comment-only fossil section (documented, zero live rules). 4 documented `!important` escalations, each justified against a real cascade/compatibility conflict (visually-hidden classes, login-prompt positioning, shipping radio dot, accordion-option radius) — not sloppy, but worth normalizing/reducing in a rebuild.
- `assets/checkout/checkout-desktop.css` (~220 lines) — `min-width: 1024px`-gated, `.wc-block-components-sidebar-layout` is the sole two-column authority (1 more `!important`, same justification pattern). Breakpoint tiers: `<768` mobile wizard, `768–1023` plain tablet, `1024–1439` two-column fluid, `1440–1799` fixed 460px rail, `≥1800` 1480px canvas/480px rail.
- `assets/checkout/checkout-order-summary.js` (~54 lines) — correct pattern to imitate: uses Woo's documented `itemName` checkout filter, no DOM hacking.
- `drywalltoolbox/wp/wp-content/mu-plugins/dtb-commerce/Validation/CheckoutFieldPolicy.php` — as of v17, collects name once via native shipping/billing fields (the old dual `dtb/first_name`/`dtb/last_name` Additional-Checkout-Field hack and its client-side sync workaround were **removed** in v17 after causing a real production Stripe payment-confirmation failure in v15 — "Missing required param: billing_details[name]"). This history is the clearest evidence in the whole audit of why DTB must not duplicate identity/payment state.
- `Payment/StripeElementAppearance.php` — Stripe Appearance API only (`wc_stripe_get_element_options`), correctly boundary-respecting; never touched by prior redesign passes and must not be touched by this one either.

Full prior audit with root-cause ranking lives at repo root: **`CHECKOUT_UI_AUDIT.md`** (dated 2026-08-06) — read this first in the next session, it has the full v1–v17 changelog, the complete "what must never change" contract list, and a prior rebuild-vs-refactor recommendation that this session's WooCommerce-core investigation (below) supersedes on one specific point (native accordion availability).

## Decisive new finding this session added: WooCommerce core has no native accordion mechanism for checkout steps

Investigated the local mirror of the live WooCommerce plugin at `drywalltoolbox/wp/wp-content/woocommerce` (WC 11.0.0 / Blocks 11.8.0-dev, merged into core). Confirmed directly from the compiled bundles and PHP source:

- Woo's internal `CheckoutStep` component's `disabled` prop is real but **not publicly exported**, **not reactive** (plain prop from parent), and semantically means "render as `<fieldset disabled>`" (form-gating for incomplete steps) — **not** a visual collapse/expand accordion state. There is no `aria-expanded` toggle, no height animation, nothing to hook.
- Exhaustive search of every shipped JS bundle for `activeStep`/`currentStep`/`stepIndex`/`setActiveStep`/`useCheckoutSteps` — **zero matches**. `wc/store/checkout`'s real action set only covers processing lifecycle (idle/before-processing/after-processing/complete/has-error), validation errors, and customer/order data — nothing about which step is open.
- The checkout filter registry (`registerCheckoutFilters`/`applyCheckoutFilter`) is real and enumerable, but every actual filter name in the shipped bundles is cart/order-summary cosmetics only (`itemName`, `cartItemPrice`, `totalLabel`, `placeOrderButtonLabel`, coupon notices, etc.) — **nothing exists for step order, step labels, step visibility, or field placement beyond registration order.**
- `CheckoutFields` PHP confirms exactly 3 fixed field-location slots (`contact`, `address`, `order`), no ordering/priority option — matches what DTB's docs already assumed.
- Woo does ship a generic, `__experimental` `accordion-group`/`accordion-item`/`accordion-header`/`accordion-panel` block set (Interactivity API-based) used for FAQ-style content elsewhere on the site — **not wired into Checkout anywhere**, not importable into a checkout context, but usable as an **ARIA/interaction pattern reference** (native keyboard-accessible header/panel semantics) for a bespoke build.
- The one real supported structural extensibility lever is `registerCheckoutBlock` (registering into Woo's own named inner-block slot areas around Contact/Shipping/Payment/Order-summary), which is the *supported* way to inject markup — as opposed to reading rendered DOM class names the way `checkout.js` currently does for step classification (even though v17 narrowed that to stable per-block identity classes, it is still classification of Woo's rendered output, not a registered extension point).

**Conclusion: an accordion checkout cannot be built on any native WooCommerce Blocks mechanism.** The two real options are:
1. **Plain single-scroll layout** — drop the fake wizard entirely, ship the well-styled Checkout Block as one continuous scroll (this is already what happens today at ≥768px, so the "does it work" question is already answered — it does). Zero custom step-tracking JS, lowest risk, matches how WooCommerce actually wants to be extended.
2. **Bespoke accordion shell** — build DTB's own collapse/expand chrome (height-animated, `aria-expanded`-driven, `prefers-reduced-motion`-respecting) wrapped around Woo's rendered inner-block groups, ideally located via `registerCheckoutBlock`'s stable slot areas rather than the current DOM-class classification approach. This is real, deliverable work — not a native feature flip — and must keep Stripe's Payment Element mounted-but-hidden (never `display:none` at the exact moment Stripe's Payment Element mounts, since Stripe does iframe layout math on mount — use visibility/height-collapse techniques and trigger a resize/re-layout on first expand).

Both options are compatible with everything `CHECKOUT_UI_AUDIT.md` already found sound (the CSS restyling layer, the Stripe Appearance API integration, the `itemName` filter pattern) — neither requires touching those.

## Recommendation for the next session to execute against

**Go with option 2, bespoke accordion, but scoped as a true rebuild of the interaction layer only** — not a fourth rewrite of the DOM-classification heuristic. Concretely:

1. Reuse v17's `classifyStepGroups()` mechanism as the "which rendered nodes belong to which conceptual section" layer (it's now correct and stable — keyed off real per-block identity classes, no more document-order fallback). Do not redesign step *detection*.
2. Replace only the *chrome*: swap `buildRail()`/`buildActionBar()`/`goToStep()`/full-screen `inert` swap for expand/collapse-per-section chrome — collapsed-by-default accordion headers, one section open at a time (or allow multiple open — decide in next session), auto-collapse-on-valid-completion instead of a hard-gated Continue button, scroll-to-first-invalid-field on submit attempt instead of blocking forward navigation.
3. Extend the accordion pattern to **all breakpoints**, not just mobile — this directly answers the original question ("should this be fluid/responsive across devices, not just a mobile toggle"). Desktop/tablet currently get a silently different (plain single-scroll) experience; unifying on one accordion-or-scroll model everywhere removes the `<768` / `768–1023` / `≥1024` three-way behavioral split that `checkout.js`/`checkout-desktop.css` currently maintain as separate code paths.
4. Port the SPA's canonical motion tokens (`--dtb-ease`, `--dtb-ease-standard`, `--dtb-ease-emphasized`, `--dtb-fast`/`--dtb-normal`/`--dtb-slow` from `frontend/src/styles/storefront-tokens.css`) into `checkout.css`'s own `:root` block by value (renamed to avoid the existing `--dtb-*` name collision with different values) — this file has zero build-step access to the SPA's actual CSS, so this must be a manual, deliberate value port, not an `@import`. This is what makes the accordion animation feel like "one system" with the rest of the site rather than a bespoke one-off.
5. Preserve every item in `CHECKOUT_UI_AUDIT.md`'s "What Must Never Change" section verbatim: Woo Checkout Block is the only order-creation surface, `stripe_upm` is the only payment authority, Stripe styling stays Appearance-API-only, one field set / one payment state / one native "Place order" button, no writes into `wc/store/cart` beyond what's already proven safe, checkout/order-pay/callback endpoints stay non-cacheable, script enqueue order (`dtb-checkout` priority 30 → `dtb-checkout-desktop` depends on it) stays deterministic.
6. Log the change as a new numbered entry (**v18**) in `docs/checkout/checkout-ui-architecture.md` per that doc's own established convention, satisfying its entry criteria (native fields/provider surfaces stay mounted, `!important` stays justified-only, full validation matrix before sign-off).
7. Required pre-ship verification unique to this rebuild: confirm Stripe's Payment Element visibly resizes/paints correctly the first time its accordion section is expanded (not just on initial page load) — real device, not just devtools emulation, since SiteGround's bot/WAF layer has previously blocked automated/headless verification (see v16's "unconfirmed live" history — don't repeat that pattern for this change).

## Decisions made (confirmed by user — supersedes the "open decisions" this doc originally listed)

- **Single-open accordion, smooth and seamless.** Expanding a section auto-collapses the others. One section open at a time, always. Transition must read as fluid/animated (height + opacity, respecting `prefers-reduced-motion`), not an instant snap — this is a headline UX requirement, not incidental polish.
- **Scope is small-screen/mobile only.** Do **not** unify desktop/tablet into the accordion model. Desktop (≥1024px) and the 768–1023px tablet tier keep their current plain single-scroll behavior via `checkout-desktop.css`/default Woo Blocks layout, untouched. This rebuild is scoped to `checkout.js`'s `<768px` `MOBILE_QUERY` path and `checkout.css`'s mobile-first rules only — `checkout-desktop.css` should not need functional changes (only touch it if something in the mobile rebuild leaks upward, which it shouldn't given the existing `min-width: 1024px` gating).
- **No blast-radius restriction — full production-readiness bar.** This is a complete rebuild of the mobile checkout UI/UX, not a minimal chrome swap. In addition to the wizard→accordion chrome replacement, the next session should treat this as license to modernize whatever in the mobile checkout surface needs it: visual design (spacing/type/elevation polish), interaction/motion quality, accessibility correctness, and cleanup of known rough edges — all while still respecting the hard "must never change" contract items (Woo Checkout Block as sole order-creation surface, Stripe Appearance-API-only styling, one field set/one payment state/one native submit button, deterministic enqueue order).
- **Token strategy: full rebuild of `checkout.css`'s mobile token set, not just motion-token porting.** Since this is now a complete mobile rebuild with no blast-radius limit, design the token layer properly: port/adapt the SPA's canonical values (motion easings/durations from `frontend/src/styles/storefront-tokens.css`, plus reconcile color/radius/spacing naming so `--dtb-radius-lg` etc. aren't silently different numbers between the two systems) into a clean, internally-consistent `:root` block in `checkout.css`. Still a manual value port (no build-step/`@import` access from this server-rendered template — confirmed in this session), but don't half-do it; this is the one file governing all mobile checkout visual language, so its tokens should be authoritative and complete on their own terms.
- **Fold in the incidental cleanup from `CHECKOUT_UI_AUDIT.md` Finding 3** as part of this rebuild: remove the harmless CSS fossil comment block, normalize the `checkout.css` (`0.001ms`) vs `checkout-desktop.css` (`0.01ms`) reduced-motion inconsistency (desktop file likely doesn't need touching if truly untouched — verify whether normalizing requires touching it or if `checkout.css`'s own value can just be corrected in isolation), and generally leave the mobile CSS in a state with no dangling dead code.
